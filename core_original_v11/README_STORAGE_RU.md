# ORACLE CORE v1.1 — умное хранение данных без потери исследовательской истории

Проект основан на ORACLE v1.0; сохраняет сборщики, модели, журнал сигналов и веб-панель.
Это сборка для установки, а не подтверждение, что ORACLE уже запущен на VPS.

## Что добавлено

1. **Сжатие старых версий источников** (`storage.py`): lossless zlib для JSON, только если факт уже прошёл очередь извлечения знаний и есть более новая версия того же источника. ID, дата получения и контрольная сумма не меняются; последняя актуальная версия остаётся доступной обычным потребителям.
2. **Parquet/ZSTD для завершённых месячных архивов свечей**: только для успешно импортированных и проверенных наборов Binance, не моложе 45 дней. После создания проверяется число записей и SHA-256 содержимого после обратного чтения. Удаление из активной SQLite и запись манифеста выполняются в одной транзакции. При ошибке исходные свечи не удаляются. Чтение этих разделов подключено в `research.get_candles`. Требуется бесплатная Python-библиотека `duckdb`, которая теперь включена в `requirements-ml.txt`.
3. **Честные резервные копии**: онлайн `sqlite3.backup` с проверкой `quick_check`, gzip-сжатие и контрольная сумма; до 7 последних разных копий (идентичные не дублируются); по умолчанию бюджет локальных копий ограничен `ORACLE_BACKUP_MAX_GB=12` ГБ, но две новые копии сохраняются всегда. Архивы Parquet зеркалируются *только при первом появлении или изменении* с SHA-256-проверкой; копии не перезаписываются вслепую.
4. **Автоматическое обслуживание**: архивирование и сжатие каждые 6 часов (не более 500 версий источников и одного месяца свечей за цикл); копия SQLite раз в сутки, лог-ротация, защита от нехватки места. При падении источника или повреждении архива никакие сигналы из неполной истории не считаются достоверными.
5. **Раздел телеметрии хранения**: `/api/storage` и блок «Хранение и сжатие» в разделе «Сводка за сегодня». Отображаются фактические размеры БД, архива, бэкапов, свободное место и число архивных разделов.

## Где находятся данные

- `oracle.sqlite3` / `ORACLE_DB` — SQLite и индекс `candle_archives`.
- `archives/` / `ORACLE_ARCHIVE_DIR` — Parquet/ZSTD; обязателен для воспроизводимости истории.
- `backups/` / `ORACLE_BACKUP_DIR` — резервные копии SQLite **и** `archive_mirror/`.
- `model_artifacts/` — модели. Нужно сохранять вместе с БД.
- `logs/` — технические журналы (не являются доказательствами прогнозов).

**Важно:** пока `backups/` находятся на том же физическом сервере, они НЕ защищают от потери самого сервера. Для настоящего offsite-backup подключите отдельно смонтированный внешний том либо репликацию в независимое хранилище. Без этого не называйте копии внешними.

## Первый запуск на Mac

Распакуй архив. Если старая версия ещё НЕ работала:

```bash
cd ~/Downloads/ORACLE_CORE_v11
bash install_mac.sh
```

Если установлен ORACLE v1.0, сперва останови старые службы (они перестанут работать, но данные останутся):

```bash
cd ~/Downloads/ORACLE_CORE_v10
bash uninstall_mac.sh
cd ~/Downloads/ORACLE_CORE_v11
python3 upgrade_from_v10.py --from ~/Downloads/ORACLE_CORE_v10
bash install_mac.sh
```

Если проект лежит в другой папке — замени пути. Миграция копирует БД через SQLite backup, `.env`, модели и архивы, отказывается затирать уже существующую целевую БД и не удаляет прежнюю папку.

## Запуск на Linux через Docker

Docker + Compose v2. В новой папке ORACLE:

```bash
docker compose up -d --build
docker compose exec -T research python storage.py report
docker compose exec -T research python storage.py verify
docker compose ps
```

Веб-панель слушает только `127.0.0.1:8765` на сервере; подключайся через защищённый SSH-туннель.

**Если на сервере уже запущена v1.0:** сначала `docker compose down` в старой папке (без `-v`!), сохрани старые `.env`, `model_artifacts` и `backups`. Перенеси эти директории в новую папку или подключи их как существующие bind mounts. Новый `compose.yaml` фиксирует `name: oracle_core_v10`, чтобы использовать стандартный Docker-том `oracle_core_v10_oracle-data`, созданный v1.0 при обычном `docker compose up`. Если старый Compose запускался под другим именем проекта, **сначала** проверь существующие тома через `docker volume ls`; не запускай новую версию, пока не указан правильный том. База без этого может казаться пустой. Удобно проверить через `docker compose config`.

Архивное хранилище — новый отдельный том `oracle-archives`; модели читают и живую SQLite, и Parquet-архивы. Нельзя удалять ни БД, ни этот том.

## Проверка хранения

```bash
python3 storage.py report
python3 storage.py verify
python3 storage.py once
python3 -m unittest discover -s tests
```

`storage.py once` делает один ограниченный цикл. Система не удаляет первичные исторические данные, если не удалось создать и проверить архив.

Команда `python3 storage.py vacuum` существует **только для редкой ручной профилактики при остановленных рабочих процессах**: SQLite после архивации обычно повторно использует освобождённые страницы, но не сразу уменьшает файл. VACUUM требует свободного места примерно вдвое больше размера базы; она откажет при свежих heartbeat. Во время непрерывной работы VACUUM автоматически не запускается.

## Экономия и реальные ограничения

- Сжатие и архивирование без потерь — экономия зависит от конкретного набора данных. Заранее обещать «минус 75%» нельзя.
- Диск 140 ГБ — стартовый объём, **не бессрочный лимит на все мировые данные**. Когда он заполняется, систему потребуется масштабировать; никакой код не превратит 140 ГБ в бесконечное хранилище.
- «Инкрементальными» в этой версии являются зеркальные копии *неизменяемых Parquet-файлов*. База SQLite резервируется полностью, но сжимается и пропускает идентичные предыдущему снимки. Это не настоящий блочный инкрементальный backup.
- Без доступного `duckdb` Parquet-архивация **пропускается**, а исторические свечи остаются в SQLite; это безопаснее, чем удалять их.
- Автоматическое сжатие старых источников не затрагивает свежие версии, а также новости и данные, ещё не обработанные `knowledge.ingest`.
- Отдельные платные сервисы не подключаются, реальные сделки и ставки отключены.

## Планировщик

`brain_daemon.py`:
- `storage`: каждые 6 часов;
- `backup`: каждые 24 часа;
- `backfill`: тормозится при менее чем 8 ГБ свободного места.

Состояние: `python3 brain_daemon.py status`.
После деплоя нужно один раз проверить наличие реальных данных и размер резервных копий; система не может доказать непрерывную работу до запуска на VPS.
